ZFS Under Proxmox

scenario
depth 2/3 − deeper + surface

Proxmox is a popular system for running virtual machines—computers simulated in software—on one physical box, and it offers ZFS during installation. This is how most home servers end up running ZFS for years without their owners ever meeting it: click yes, machines appear, storage works. The natural assumption—each virtual machine's disk is a big file sitting in a folder somewhere—sends you hunting for files that don't exist. Actually, Proxmox carves each virtual machine's disk straight from the pool (a zvol—a slice of the pool pretending to be a real disk), and the mysterious rpool is just the pool the installer made for the operating system itself. (Operational source: the practitioner's own Proxmox hosts run exactly this stack.)

Decoding a typical host:

  • zpool status—rpool (the installer's, often a mirror of the boot disks) plus any pool you added. All the vdev/scrub/status reasoning from this site applies verbatim.
  • zfs list—rpool/ROOT/... (the OS), rpool/data/vm-103-disk-0 and friends (zvols, one per VM disk), and on a services host, datasets like tank/services/<name> per deployed service—filesystem face and block-device face of the same pool, side by side.
  • The RAM ledger—the ARC and your VMs share physical RAM, and the give-it-back dance is imperfect on a VM host; this is the one place capping zfs_arc_max is orthodox rather than superstition (see The ARC). Budget it deliberately: RAM = VMs + ARC cap + host slack.
  • Proxmox's own VM snapshots ride the same machinery—but sanoid policies on the zvols and syncoid replication offsite are what turn "snapshots exist" into a strategy (see Sanoid and Syncoid).
